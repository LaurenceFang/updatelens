# Core collection, rules and export

Node entry: `src/core/index.ts`. Browser entry: `src/core/pure.ts` (contains no filesystem imports). The backend must register project IDs and canonical root paths; API requests select IDs only. The collector itself also enforces canonical roots, rejects duplicate roots/IDs in batch mode, and rejects a batch larger than three roots.

## Collection boundary

The collector reads only `.claude/settings.json`, `.mcp.json`, `.codex/config.toml`, root `AGENTS.md`/`CLAUDE.md`, `package.json`, `pyproject.toml`, `requirements.txt`, `.gitlab-ci.yml`, one level of `.github/workflows/*.yml|yaml`, and `.claude|.agents/skills/<name>/SKILL.md`. It does not traverse a source tree, follow declaration references, read a global config, read `.env`/`settings.local.json`, execute a package script, use a shell, or inspect Git authors/messages/remotes/history.

Configuration-location references verified 2026-10-03: [Claude project MCP](https://code.claude.com/docs/en/mcp#project-scope), [Codex project config](https://learn.chatgpt.com/docs/config-file/config-basic), [Codex repository skills](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills). Root `.agents/skills` is supported; nested working-directory skill discovery and legacy `.codex/skills` are outside this bounded collector.

Limits: three roots, 64 files, 48 KiB per file, 512 KiB total, 64 directory entries before omitting an oversized declaration directory, 12 skills per product directory and 24 workflow files. Unsupported names and extensions are omitted. Every existing path component is checked using `lstat`/`realpath`; symbolic links and junctions are refused even when their target is inside the root. Reads use handles, a bounded buffer, leaf no-follow where supported, identity checks, and a second component check. Node path checks reduce path-change races; they are not an OS sandbox against a malicious process replacing directories during the exact read interval. Local mode assumes registered roots are controlled by the user.

## Meaning and limitations

JSON structure is parsed; malformed JSON produces a visible partial scan. TOML/YAML recognition deliberately extracts only allowlisted declaration keys and CLI references, rather than claiming full syntax validation or semantic loading. TOML project trust, config precedence, hook execution, scripts and installed versions remain unverified. Arbitrary instruction prose is never forwarded as an instruction. Config values, MCP names/URLs, command arguments, dependency versions and skill descriptions are omitted. Only known field names, events and CLI flags are retained. CI references are approximate declaration evidence, not proof of executed CI.

Every evidence item has a stable ID, relative path, field or recognized line, type and explicit product-channel association. Generic `AGENTS.md` presence has no product association; a known config path reference may establish a bounded association. Claude-only declarations do not match Codex CLI changes. CLI evidence does not establish Codex desktop applicability. Mixed CLI strings keep flags attached to their respective product segment.

Recency is a disclosed approximation derived only from the newest successfully read declaration file modification timestamp: `max(0, 100 - 5 × whole days since modification)`. It is not true user activity, does not establish runtime use, and synthetic fixtures have no measured activity. No last-commit timestamp is currently collected.

Rules separate source fact, local observation, inference and action. Official adapter feature tags support feature-level hypotheses; explicit shared documented signal/flag supports a direct association, never a proven incompatibility. Unrelated means no association within the selected workflow and bounded evidence. Selected features without evidence and empty/global-only projects remain unknown. All rule findings use informational severity; confidence is association strength. Actions recommend comparing documented behavior; they do not invent official migration commands or executed test outcomes.

Findings group by project, association kind and feature; missing-evidence and unrelated observations each collapse to one summary per project. Named signals appear first, then feature hypotheses. At most six groups per project are displayed; overflow is consolidated with all source/evidence references retained. Every selected release and change remains in the report; the group source summary includes at most three statements and discloses additional retained statements. Suggested actions name shared signals and cited declaration locations where available. Group and report IDs are scoped to immutable review context: channel/range/workflow, selected source IDs/content and sanitized evidence, plus a SHA-256 bounded collection-content digest when present. The digest exposes no raw content and is omitted from reports/exports and external AI payloads. Changed source/range/configuration rotates task IDs so an earlier Done report cannot silently apply to a different review; unchanged content remains stable despite new timestamps or source refresh retrieval time.

Markdown/JSON boundary sanitization strips absolute paths, secret-shaped credentials (including generated `oc_sk_` tokens), bearer/JWT/assignment secrets, URL credentials and query parameters. Arbitrary text URLs lose fragment contents; `sourceUrl` fields retain bounded non-secret anchors only for HTTPS official product documentation/repository domain and path allowlists. Export includes source/evidence IDs, source links, scan warnings, coverage and explicit disclosures that statuses/notes are user reports. Unknown encodings or arbitrary natural-language secrets cannot be universally recognized: the primary protection is omitting raw configuration values and arbitrary file contents at collection time. Provider validation must separately ensure generated prose cannot invent evidence or include paths/secrets.

## Verification

`npm test` includes core tests using synthetic files and temporary roots only. The tests exercise malformed JSON, bounded scans, disallowed files, external links, canonical-root refusal, missing/global-only evidence, product separation, mixed CLI flags, direct association calibration, stable IDs, fixture parity, redaction and exports. Root-owned real project scans and runtime/browser/provider acceptance are separate checks; unit tests do not claim those outcomes.
